# Architecture and implementation contracts

This file describes current implementation. Future capabilities and their status belong in [milestones](milestones.md).

## Application boundaries

The app is a browser-only SPA. It maintains one active OBS controller session at a time, using WebSocket v5, with RPC version 1 and the JSON build of `obs-websocket-js`. There is no application backend, account system, or proxy. Remote video uses direct browser-to-WHEP signaling and WebRTC media. A production-only service worker caches the application shell. OBS scene previews use repeated WebSocket screenshots.

Routes use React Router's `BrowserRouter`: `/` manages connections and `/studio` displays the controller. The studio route returns to connections without an active session after any startup restoration finishes. During an active connection, the connections route redirects to the studio and the brand link stays in the studio. The single **Exit** button disconnects and returns to connections; saved profiles remain available for the next session. Browser Back cannot open the connection manager while a session remains active. Static hosts need an `index.html` fallback for client routes.

Connection cards are native buttons: clicking/tapping anywhere or pressing Enter/Space starts the existing remembered-password connection or session-password prompt. The input retains its form props and ref for QR imports and native form submission.

## Session restoration after page reload

After a successful connection and initial synchronization, `StudioClient` writes only the active profile ID and normalized endpoint URL to `sessionStorage` under `studioctrl.active-session.v1`. This tab-scoped marker survives reload/browser discard without persisting live OBS state or additional credentials. Explicit Exit/Cancel, a new connection attempt, and failed restoration clear it; an unexpected socket closure leaves it available for a later page reload. There is no continuous reconnect loop for a page that remains loaded.

At provider startup, the marker must match a currently saved profile and endpoint. The provider makes one connection attempt, using only that profile's explicitly remembered password (or no password). While restoring, the shell displays Reconnecting and defers route redirects/controller content until fresh OBS synchronization finishes. Success opens `/studio`, including when the restored page started at `/`. Authentication/network/synchronization failure or a ten-second timeout returns to the connections page. Cancel disconnects immediately; stale completions/timeouts cannot replace a later manual connection. React StrictMode effect replay reuses the same attempt.

Deleted/edited profiles, malformed markers, and unavailable storage skip recovery. Passwords that were not remembered cannot survive page unloading: authentication-enabled OBS then requires a manual connection from the home page. Recovery never enables Studio Mode, selects scenes, transitions, or starts outputs. New tabs without a marker start disconnected; browser tab duplication/session restoration may copy tab storage according to browser behavior.

## Local HTTPS

`vite.config.ts` loads `.cert/key.pem` and `.cert/cert.pem` relative to the config file when running a server outside test mode. Development and Vite preview use this local TLS configuration; tests and production builds do not read or require the certificate files. `/.cert/` is ignored by Git.

The configured `server.allowedHosts` is `[".d.rodr.dev"]`, inherited by preview. This permits `d.rodr.dev` and its subdomains in Vite’s hostname matching. Vite skips that check under HTTPS, so the allowlist is configuration, not HTTPS host enforcement. The supplied certificate covers `studioctrl.d.rodr.dev`; DNS resolution and certificate trust are configured on the development machine. See [README](../README.md) for local setup and [Vite server options](https://vite.dev/config/server-options.html#server-allowedhosts) for hostname matching behavior.

## PWA and application updates

`vite-plugin-pwa` generates the root-scoped manifest and Workbox service worker during production builds. The browser title and manifest name/short name are StudioCTRL. The manifest uses standalone display, starts at `/`, and supplies PNG icons at 192/512 pixels, a separate maskable icon, and an Apple touch icon. The icons derive from the custom StudioCTRL favicon (three scene tiles and broadcast arcs); `scripts/generate-pwa-icons.ts` regenerates them using Sharp (`bun run generate:icons`). Development service workers are disabled; use a production build and preview for PWA validation.

Workbox precaches built JS, CSS, HTML, bundled fonts, and icons. Navigation fallback serves the cached shell only for `/` and `/studio` (including its trailing slash). There are no service-worker runtime caching rules for external resources, OBS connections, credentials, screenshots, or OBS state. Representative scene thumbnails use the separate IndexedDB cache described under [Screenshot previews](#screenshot-previews). Profiles and preferences remain in localStorage under their existing contracts. Opening a cached shell requires a new live OBS connection, automatically attempted when this tab has an active-session marker; shell availability does not establish OBS reachability.

Updates use `registerType: "prompt"`, with no automatic skip-waiting or client claiming. `PwaUpdate` offers **Reload to update** and **Later** when a release is waiting. Reload is disabled while this window is connecting or connected, and errors remain in the update notice. Updates may reload other open app windows, so the notice instructs the operator to disconnect OBS in each window before accepting. Closing all app windows can also allow a waiting worker to activate normally. Registration checks for updates when the app opens; there is no periodic update polling.

Host the built app at the origin root over trusted HTTPS with SPA rewrites for client routes. Serve `sw.js`, `index.html`, and `manifest.webmanifest` with revalidation (`Cache-Control: no-cache`); fingerprinted assets can use long-lived immutable caching. The service worker must be served as JavaScript, never rewritten to HTML. A valid secure app origin does not bypass browser WebSocket mixed-content or local-network restrictions; the intended OBS endpoint must be tested separately.

## Cloudflare Workers hosting

`wrangler.jsonc` configures an assets-only Worker named `studioctrl` with `assets.directory: "./dist"` and `not_found_handling: "single-page-application"`. Vite still owns the client build; there is no Worker entry point, Cloudflare Vite plugin, asset binding, or server runtime logic. The existing browser-to-OBS connection remains direct. Account selection and authentication belong to Wrangler/CI, not the committed application config. Custom domains are not configured in the repository.

`public/_headers` is copied to the build output and interpreted by [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/headers/). `/`, `/index.html`, `/studio`, `/studio/`, `/sw.js`, and `/manifest.webmanifest` receive `Cache-Control: no-cache`; fingerprinted `/assets/*` receive `public, max-age=31536000, immutable`. Other assets use Cloudflare’s defaults. `_headers` is hosting metadata and is not part of the service-worker precache. Vite preview does not interpret these hosting rules; use Wrangler to check them.

`deploy` builds then uploads with Wrangler; `deploy:check` builds then runs a local deployment dry run. `preview:worker` builds and starts Wrangler locally without the mkcert configuration. No script automatically deploys on build. Each deployment uploads the current `dist/`; the repository does not implement retention of previous fingerprinted files. Verify a two-release rollout with open windows and cached clients before production acceptance, including clients still loading an older release.

## Stable control layout

Ordinary control-state updates must not move surrounding content or flash transient disabled styling. Use `aria-disabled` with explicit event guards for temporary busy/sync states, read-only for the duration field, and native disabled styling for genuinely unavailable controls. Automatic synchronization never spins or dims the appbar actions icon. Shared buttons, inputs, and scene tiles change appearance instantly; buttons have no pressed translation. Dropdowns are non-modal by default, open without fade/zoom/slide animations, and keep page scrolling available instead of applying Radix scroll locking. The root reserves a stable scrollbar gutter so vertical overflow changes do not recenter the page.

Connection status badges have a fixed width and height across Checking/Online/Offline. Error notices are dismissible fixed overlays rather than page/dialog rows. Duration validation appears inside the open settings menu, while empty-transition feedback is positioned below its trigger outside normal flow; neither moves the centered Transition action. Preview panels and scene tiles keep their existing fixed aspect ratios, except No Preview monitors collapse below sm as described above; their frame, loading, and selection overlays stay outside normal flow.

Intentional changes such as navigation or adding/removing scenes still change the content. Verify real layout stability in a browser, especially with a visible page scrollbar; DOM tests cover menu behavior but do not measure pixels.

## OBS is the authority

Program is the current output scene; Preview is the prepared next scene in Studio Mode. A scene can occupy both. Keep their indicators independent.

`selectScene` calls `SetCurrentPreviewScene`. `selectTransition` calls `SetCurrentSceneTransition` without triggering any scene change, and refreshes state through the shared command lifecycle. `transition` calls `SetCurrentSceneTransition` before `TriggerStudioModeTransition`; this also changes the transition selected in OBS. `setTransitionDuration` validates the protocol range and updates OBS through the shared guarded command lifecycle. Duration and other transition behavior remain OBS-authoritative, including any OBS-side configuration that affects the result.

Connecting does not enable Studio Mode. `enableStudio` explicitly calls `SetStudioModeEnabled`. Studio-dependent commands are guarded in the client as well as disabled in the UI. Busy and syncing states also block commands.

## Synchronization and lifecycle

Connection state is `disconnected`, `connecting`, or `connected`; connection success and initial synchronization are separate operations. The client subscribes to scene selections, scene list/name changes, Studio Mode, scene collection changes, and current transition settings. These events request full state refreshes rather than maintaining separate optimistic scene state in React.

Refreshes share an in-flight promise and coalesce additional requests into another pass. A revision counter and client identity prevent outdated responses from overwriting a newer snapshot. Commands wait for refresh completion before returning. Collection changes clear scene selections while the new collection loads.

Transition start events lock controls. `SceneTransitionVideoEnded` unlocks them and refreshes state; `SceneTransitionEnded` alone can represent the cut point of a stinger rather than the end of playback. An app-triggered transition has a 30-second fallback that unlocks and refreshes if completion was not observed. Preserve the distinction when changing transition logic.

Disconnect clears scene state and timers. Intentional disconnect removes the old client's listeners; callbacks and asynchronous commands check client identity. Authentication failures receive a password-specific error. Reload and dropped connections require the operator to connect again.

## Output status badges

`StudioClient.getOutputStatuses()` reads `GetStreamStatus` and `GetRecordStatus` concurrently over the authenticated session. It uses OBS's `outputActive`, millisecond `outputDuration`, `outputPaused`, and `outputReconnecting` fields ([protocol](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)). Reads do not acquire command busy/syncing locks or mutate OBS. Each failed output read becomes unavailable independently; late results from an old WebSocket session are rejected.

The connected appbar calls `useOutputStatuses` with the current session profile object and shares its result between `OutputBadges`, `OutputMenuItems`, and (through `Studio`/`SceneMonitor`) the Remote Preview streaming warnings. It reads immediately, then waits one second after each completed read before polling again, with no overlapping poll cycles. Hidden tabs suspend reads and becoming visible resumes them. Disconnect/session replacement or unmount clears polling and discards pending results. A completed output command requests an immediate refresh; if a read is pending, the refresh is coalesced into a following read. Durations come directly from OBS, including sessions already active when connecting and paused recordings; the browser does not extrapolate them. Checking/unavailable badges are muted with --:--:-- and accessible status labels rather than implying an inactive output or retaining stale activity. The next successful poll recovers each badge. Status is transient and is never persisted.

The menu offers **Start streaming** / **Start recording** for inactive outputs. Active outputs show **Streaming / Recording** with their elapsed time at every viewport width. Checking or unavailable outputs have disabled menu rows. Starting is immediate; selecting an active output opens a shadcn/ui AlertDialog naming the device and asking to stop that output. Cancel/Escape leave OBS unchanged. Confirm uses an explicit stop action, disables repeats/cancellation while pending, retains the dialog with an error after failure, and restores focus to the actions trigger when closed. The confirmation belongs to its session and disappears on disconnect or profile replacement.

`StudioClient.setOutputActive(output, active)` uses the existing command lock/error handling, with no Studio Mode requirement. It re-reads the selected output, checks WebSocket identity after that read, and sends only the necessary `StartStream`, `StopStream`, `StartRecord`, or `StopRecord` request. Already-matching status is a no-op; it never toggles an output. Busy/syncing/generating sessions reject commands. The command returns success for UI confirmation handling, waits for the regular scene refresh, and never selects Preview/Program or triggers transitions. Output-control failures use existing global error feedback as well as local stop-dialog retry feedback.

## Screenshot previews

Each monitor has a separate 36px header above its 16:9 picture, with Preview/Program label, truncated scene name, the MonitorPlay source-menu button, then expand/collapse. The header never overlays the picture and remains visible in every mode. Below sm, No Preview hides the picture and retains the header row. Expanding works in all monitor modes.

Each monitor defaults to No Preview and stores its mode independently under `studioctrl.monitor.v1:<profileId>:<preview|program>` in localStorage. Only `none`, `obs`, and `remote` are accepted; invalid/missing preferences default to No Preview. Explicitly saved OBS Preview choices remain enabled across reloads; changing the default does not overwrite them. The individual menus and combined toggle subscribe through `useSyncExternalStore` to the shared monitor settings module. Same-tab writes notify all subscribers, and browser storage events synchronize other tabs. Combined writes save both choices before notifying. Storage failures retain shared in-memory preferences for the current page lifetime. Live monitor frames are transient; representative scene thumbnails are persisted separately as described below.

`StudioClient.getScreenshot(sceneName, targetWidth = 640)` uses the existing authenticated connection and calls `GetSourceScreenshot` with JPEG (`jpg`) and compression quality 65; height is omitted to preserve the scene's aspect ratio. Before each live monitor capture, the hook measures its canvas viewport width in CSS pixels and multiplies it by the current device pixel ratio. The client rounds up and clamps the requested width to OBS's 8–4096 range; non-finite/non-positive widths are rejected. Measuring per capture follows inline resizing, expansion/collapse, browser zoom, and display changes without restarting the loop. Zero-width monitors pause capture until measurable. Thumbnail collectors retain the default 640px width. Concurrent requests share only when both scene and normalized width match, so differently sized Preview/Program monitors remain independent, with at most two pending screenshot requests in the current session/collection generation. Capture is independent of command `busy`/`syncing`, and failures stay local to the monitor rather than replacing the global control error.

Each enabled live monitor runs a sequential loop capped at 10 FPS: capture, decode a candidate image off-screen, draw it to the canvas, then wait for the remainder of the 100ms frame period. Canvas pixels remain visible during decoding; image data is kept outside React's shared state. Decoded candidate resources are released after drawing, and the canvas uses `object-contain` to fit non-16:9 scenes without distortion. Failures show the scene-name fallback and retry with a 1–5 second exponential backoff. A capture/decode taking over three seconds shows the unavailable fallback while waiting for that operation; it does not enqueue replacement calls.

Hidden tabs stop requesting new frames and recheck visibility every 250ms. No Preview, missing scenes, disabled Studio Mode, Exit, and unmount stop the loop. Source changes hide the previous image immediately; an AbortSignal prevents obsolete replies/decodes from drawing. `previewEpoch` invalidates same-name scenes across connections and collection changes. Session/collection invalidation rejects pending screenshot wrappers and clears their cache; already-sent OBS requests cannot be cancelled on the wire, so late results are discarded. The next frame starts only after the previous capture and decode settle.

For OBS's `fade_transition` kind (including renamed Fade transitions), `SceneTransitionStarted` snapshots the outgoing Program, incoming Preview, configured duration, and local start time. With OBS Preview enabled on Program, the monitor crossfades two scene screenshot layers linearly for that duration; the controls/overlay remain outside the animated layer. The outgoing loop stops after the duration and the incoming canvas stays mounted through the scene swap. Cut and other transition kinds have no local animation; Preview selection never animates. Session/collection resets, Studio Mode disablement, or disabling Program previews remove the composite. The simulation follows OBS start events, including external transitions, using the last synchronized transition settings; network and screenshot latency can affect its alignment.

These are **scene screenshots**, including for the Program monitor. They are not a direct Program-output feed: the local Fade simulation, other transition effects, and uncommitted same-scene Studio edits can differ from the actual output. This limitation is available in the monitor indicator tooltip. See [preview research](preview-research.md) for OBS Blade's approach, primary sources, and the distinction between scene capture and output monitoring. Remote streams use the independent WHEP player below.

### Scene source indicators

Scene tiles show a Lucide `Video` icon at the bottom-right when they contain an OBS Media Source (`ffmpeg_source`) or VLC source (`vlc_source`), including live feeds, stopped media, disabled items, and sources within nested scenes/groups. ### Representative scene thumbnails

`StudioClient` keeps cached images in `thumbnails`; scene buttons render them behind the name and independent selection labels. The selected Preview monitor uses the same cached image in OBS Preview mode until its media naturally reaches a representative position, and as a fallback when a live frame is black or unavailable. Enabled native video capture devices bypass the media-position gate, so mixed camera/media scenes use live scene screenshots even when a media input is stopped or unavailable. Playing non-local FFmpeg Media Sources with an unknown duration also qualify for live screenshots: `GetMediaInputStatus` must report PLAYING with no positive finite duration, and `GetInputSettings` must identify `ffmpeg_source` with `is_local_file === false`. Null, zero, negative, and non-finite durations count as unknown. Duration alone is insufficient because unloaded/failed video files also lack it. Local files and known-duration network videos retain the ordinary media-position/cache rules. Settings are checked only for playing unknown-duration candidates, failures keep the conservative cache path, and source settings/URLs are not persisted in controller state. The monitor shows **Video Preview** 4px above the bottom edge while the cached image is displayed, with a bottom-quarter gradient fading from 90% black at the bottom through 60% black at 40% of its height to transparent at the top behind the label for contrast; live frames have neither this label nor its gradient. Cached monitor images always display at 75% opacity against the black monitor surface, without a delay or animation; overlay text stays fully opaque. No Preview mode still shows the scene name; the Program monitor always uses live screenshots when enabled, including black output.

A single sequential studio collector runs once per second after the previous read completes, skips hidden tabs and busy/syncing/generating states, and only captures missing thumbnails for the current Preview and Program scenes. It follows enabled nested scenes/groups, detects native video capture devices (`macos-avcapture-fast`, `macos-avcapture`, `av_capture_input`, `dshow_input`, `v4l2_input`), deduplicates FFmpeg/VLC sources, and uses the first playable source with a finite positive duration and cursor, requiring that source to be at or past 5 seconds (half the duration for clips shorter than 10 seconds). Unavailable sources, failed status reads, and unknown-duration streams do not block a later usable source; scenes with media but no usable file or qualifying live source remain ineligible for natural capture. Scenes with an enabled capture device or a qualifying playing live Media Source, and non-media scenes, need no cursor check. Capture-device scenes skip media-status reads for preview eligibility and missing-thumbnail capture; the screenshot must still pass the non-black check. Hidden devices and devices under disabled parents do not qualify; audio capture inputs do not qualify. Device detection uses the input kind rather than its editable name. Third-party video-device input kinds are not automatically recognized. Automatic capture never activates a scene, restarts media, or seeks. A 32×18 decoded sample must have more than 1% of pixels with at least one RGB channel above 16; black/near-black frames are retried rather than cached. This heuristic can reject intentionally dark scenes. The Preview monitor uses the same sample rule before drawing a live frame.

`preview-cache.ts` stores JPEG data in IndexedDB database `studioctrl.previews.v1`, store `frames`, keyed by endpoint URL, current scene collection name, and scene UUID (name fallback for simulators/older responses). Refreshes hydrate the current collection's thumbnails; session/collection epochs reject obsolete captures and hydration. Storage failure leaves images available in memory for the session. Cached images survive reloads, can become stale after source edits, and are replaced by explicit generation. OBS actions → Scenes → **Reset Previews** immediately clears in-memory thumbnails and removes the saved entries for every current scene in the connected endpoint/collection, including hidden scenes. It invalidates pending thumbnail hydration/capture through previewEpoch, serializes IndexedDB deletion against cache reads/writes, and discards pre-reset reads/writes. The local action sends no OBS requests and leaves scene selections, hidden flags, profiles, and monitor modes unchanged. It is blocked while syncing/busy/generating, works without Studio Mode, and reports deletion failure with retryable error feedback. Both global **Reset Previews** and per-scene **Reset preview** use the Lucide `ImageOff` icon. Scene context menus separate the Generate/Reset preview actions from Hide/Show scene with a separator. Each scene context menu also offers **Reset preview**, using the same guards and invalidation while deleting only that scene’s in-memory and saved image, including revealed hidden scenes. Other thumbnails remain, and Preview readiness is cleared only when resetting the selected Preview scene. Normal automatic collection or Generate Previews can rebuild cleared thumbnails afterward. Other connections/collections are retained. Browser site-data clearing removes all stored images. They are illustrative stills, never authoritative output state or evidence of an OBS connection. Live media positions and session state remain unpersisted.

**Generate Previews** processes scenes sequentially while controls are guarded and a fixed progress notice is visible. It temporarily selects each eligible scene on Preview, tries media sources in traversal order, restarting stopped/ended media if necessary and waiting up to about two seconds per candidate for known-duration playback. Unavailable inputs and source-specific request failures are skipped; the first source that can be sought is moved to `min(5000, duration / 2)` milliseconds, then later sources are left untouched. Already playing network sources recognized as live are excluded from seeking/restart/restoration; their rendered scene can still be captured. Generation captures the whole scene, including when no media candidate succeeds, and retries capture for about two seconds until a usable frame arrives. Seeks can land before the requested time at a keyframe. Failed scenes retain any previous thumbnail and generation continues. Failure to restore an unavailable input does not prevent restoring other touched sources; session/Preview ownership and Program guards still stop cleanup mutations. Scenes containing media already active on Program use read-only scene capture with the same non-black retries, without selecting Preview or issuing any media commands. This also allows single-scene regeneration of live feeds shared with Program; a previous thumbnail is retained if no usable frame arrives. Program activity is rechecked before each media mutation. Generation never triggers a transition or selects Program.

Generation restores touched playing/paused media cursors and playback states, stops media that was initially inactive, and returns to the original Preview while it still owns that selection. NONE/ENDED states cannot be recreated exactly and restore as STOPPED. OBS activation settings may reset media when switching scenes, so restoration is best effort. An external Preview change, disabled Studio Mode, a new session/collection, or a source becoming active on Program stops mutations; cleanup does not overwrite an operator's new Preview or modify newly active Program media. OBS requests already sent cannot be cancelled atomically against external changes. VLC, unknown-duration media, missing files, and differing source activation settings still need broader live acceptance.

## Active media seeking

Below the scenes row, each Active media section displays a named range input with elapsed/total time per OBS Media Source (`ffmpeg_source`) or VLC source (`vlc_source`) on Preview or Program. `StudioClient.getActiveMedia` discovers inputs through `GetInputList`, checks `GetSourceActive.videoActive` for Program membership, and traverses the current Preview scene through `GetCurrentPreviewScene`, `GetSceneItemList`, and `GetGroupSceneItemList`. Traversal follows only enabled scene items, handles nested scenes/groups with a visited set, and excludes sources under disabled parents. `videoShowing` is not used because it can also refer to unrelated projectors or properties windows. Eligible inputs are read through `GetMediaInputStatus`. Other input kinds, including third-party media plugins, are currently outside this discovery contract.

The Active media heading is a keyboard-accessible disclosure button with an expanded state and a chevron. Its background stays transparent, including on hover, in both states; only the chevron changes appearance when toggled. It defaults to expanded and saves its collapsed preference globally for this browser in localStorage under `studioctrl.active-media.collapsed.v1`, across profiles, reconnects, and reloads. Missing, malformed, or unreadable storage defaults to expanded; failed writes leave the toggle usable for the current mount. Collapsing unmounts both groups of controls and discards local scrub drafts while discovery polling continues. Reopening uses current polling results. The heading still disappears when no controllable media remains. Only this UI preference is persisted, never OBS media state.

The media area has two equal columns above 900px: Preview on the left and Program on the right. At 900px and below, the sections stack with Preview first. Each section keeps its heading and an empty-state message when the other side has media, so Program never moves into the Preview column. A source appears once per section it belongs to, with independent Preview and Program labels. Shared sources appear in both sections, use the same OBS playback cursor, and include an accessible note that playback controls and seeking also change Program playback. Both sections use the same polling results and command methods; rendering a shared source twice does not add OBS reads. Independent cueing requires separate OBS source instances. The controller does not change the source's playback settings; OBS's restart-on-activation setting can reset a cue when taking the source to Program.

Each row has a fixed-width Play/Pause button and a separate Stop button beside the seeker. Active media snapshots include a `live` flag using the same non-local FFmpeg/unknown-duration source check as preview readiness, without requiring PLAYING for source classification. The media UI filters out live sources entirely in both Preview and Program, including while paused/stopped: no source row, labels, time, playback buttons, seeker, or shared-source note is rendered. When all active sources are live, the Active media section is omitted; with mixed sources, normal file rows and the existing per-side empty states remain. Local files with unknown duration retain their disabled seekers, and known-duration network files retain normal file controls. Changing a file source to live removes its row and clears obsolete scrubbing drafts; no source configuration or classification is persisted. `StudioClient.setMediaPlayback` rechecks Program activity, enabled Preview membership, and media state through the shared command lifecycle before sending `TriggerMediaInputAction`. Pause sends `PAUSE` while playing; Play sends `PLAY` while paused and `RESTART` when stopped or ended. Repeated play/pause requests matching the current state do nothing. Stop sends `STOP` while playing, paused, opening, or buffering. Play/Pause is unavailable during opening/buffering or unknown/error states; Stop is unavailable once stopped/ended or in unknown/error states. Playback buttons do not require a known duration. Failed polling disables them; temporary busy/syncing uses `aria-disabled` with event guards and preserves their normal appearance. Playback state updates optimistically on click: Play immediately shows Pause, Pause shows Play, and Stop shows Play with Stop and seeking unavailable. Both copies of a shared source use the same optimistic state. Playback and seek commands share a polling revision guard: reads started before a command or before its acknowledgment cannot replace the displayed snapshot. A fresh successful read started after acknowledgment restores OBS authority, even if OBS reports a different state; discarded/failed reads retain optimism. While a playback command is pending, per-source event guards and `aria-disabled` prevent further playback or seek actions. `setMediaPlayback` returns whether a playback action was acknowledged in the current session/collection; unsuccessful, skipped, or invalidated commands immediately restore the last polled state. Unmount clears pending playback state and ignores late completions. Playback optimism is never persisted. Stopped media, including optimistic Stop, displays the disabled seeker at zero with `--:-- / --:--`, regardless of a retained OBS cursor/duration or a pending seek position. Play/Pause does not advance/reset the displayed cursor locally. Command failures use the global error notice. Playback commands never change scenes or trigger transitions, and pending actions are discarded after a session/collection or synchronization revision change.

The component polls sequentially one second after each completed read, without setting global busy/syncing flags, and skips reads in hidden tabs. `getActiveMedia` returns `null` for unavailable or invalidated reads (session/collection, Studio Mode, or synchronization revision changes), distinct from a successful empty list. The component ignores discarded reads, preserving rows, scrub drafts, pending optimistic positions, and existing error state until a current poll succeeds; playback-triggered refreshes therefore do not briefly hide the controls. Unmount stops scheduling and discards late results; connection/collection epochs remount the list and prevent obsolete client results from being used. A failed poll preserves existing rows, disables their sliders, and displays a dismissible fixed error notice while retrying. No media state or playback position is persisted.

Media seekers use the shadcn/ui Slider from the configured Radix Lyra preset with a 1ms step so scrubbing and OBS updates retain millisecond precision. A custom key-down handler prevents Radix arrow movement and applies exactly +1,000ms for Right/Up or -1,000ms for Left/Down, preserving the fractional-second offset and clamping to zero/duration. Repeated key-down events accumulate in the pending draft; key-up commits once. Radix supplies pointer movement and other keyboard navigation, including Home/End. The app guards unavailable/busy input and commits on pointer release, key-up, or blur. The controlled value is a single-element array, with `onValueChange` updating the local draft. The local Slider wrapper exposes `thumbProps` so the accessible source name, playback time, shared-source description, disabled state, and optional thumb content reach the focusable slider thumb. During pointer dragging, a time tooltip is absolutely positioned above that thumb and follows the local scrub position. It is linked through `aria-describedby`, ignores pointer events, and does not change layout. Release, cancellation, blur, or lost pointer capture hides it; keyboard movement and unavailable/busy sliders do not show it. Unavailable sliders use Radix disabled styling; temporary busy/syncing keeps the same thumb and normal appearance with `aria-disabled` and event guards. Sliders preserve local drafts during polling and commit once on pointer release, keyboard key-up, or blur through `StudioClient.seekMedia`. Pointer cancellation discards the draft. On commit, the media area keeps an optimistic position per source for both the slider and elapsed time, shared by its Preview/Program copies. Polls started before the seek or while its command is pending cannot replace that position or the displayed media snapshot. After OBS acknowledges the command, the next successful read started after acknowledgment atomically replaces the optimistic position with OBS state, including any correction or playback advancement. Failed polls retain the optimistic position with disabled controls until recovery. `seekMedia` returns whether `SetMediaInputCursor` succeeded in the current session/collection; failed, skipped, or invalidated seeks restore the last OBS position. Per-seek identity guards prevent an older completion from clearing a newer optimistic position. Unmount clears pending positions and ignores late command completions. Optimistic positions are never persisted.

Only playing/paused sources with a positive finite duration are seekable; unknown duration or unavailable playback disables the slider. Busy/syncing uses `aria-disabled` and event guards. Seeking rechecks Program activity, enabled Preview membership, and current playback duration, validates an integer millisecond cursor within bounds (OBS does not enforce the upper bound), and calls `SetMediaInputCursor` through the shared guarded command lifecycle. Reads and seeks discard results if the session/collection or OBS synchronization revision changes while they are pending. It never selects a scene or triggers a transition. A successful seek response acknowledges the request, not exact positioning. With local FFmpeg media, OBS can seek backward to a keyframe and report an earlier cursor; the app must accept that fresh cursor instead of holding an optimistic value indefinitely. Targeted live evidence is recorded in [milestones](milestones.md); broader playback/browser acceptance remains outstanding.

## Profiles and passwords

Profiles are stored under `studioctrl.connections.v1` in localStorage with `id`, `name`, `url`, `rememberPassword`, and an optional `password`. Valid URLs use `ws://` or `wss://`, with no embedded credentials or fragment. Loading tolerates malformed storage and filters invalid entries.

Only explicitly remembered passwords are persisted; opting out removes the password on save. Non-remembered passwords are requested when connecting. The live session snapshot omits the profile password. Remembered passwords are stored without encryption, as disclosed by the connection form.

The add-connection form offers **Scan QR Code** using `qr-scanner` for camera capture or a local image/screenshot. Decoding stays in the browser; images and raw QR payloads are not persisted. `parseObsQr` accepts `obsws://host:port/password` and `obswss://host:port/password`, maps them to `ws://`/`wss://`, validates the host and port, and percent-decodes the password. The password segment is optional for authentication-disabled OBS. This follows [OBS QR generation](https://github.com/obsproject/obs-websocket/blob/master/src/forms/ConnectInfo.cpp). Scan errors never echo the credential-bearing payload.

A valid scan fills only the address and password for review; it does not save, connect, or enable password remembering. Camera capture starts only after the Scan action and is stopped on success, cancellation, dialog close, or unmount, including permission requests that settle after cleanup. Camera failures leave local image upload and manual entry available. Camera access requires browser permission and a secure context.

Changes to the persisted schema need an explicit migration/compatibility decision. Keep credential handling within the profile and connection boundaries.

## Saved connection reachability

Each connection card shows a top-right Checking, Online, or Offline badge. `isObsOnline` opens a temporary JSON WebSocket and requires a valid OBS Hello (opcode 0, a WebSocket version string, and RPC version at least 1) within five seconds. It then closes the socket. The probe sends no Identify message, credentials, or OBS commands, so it works with password-protected endpoints without creating additional controller sessions.

Badges check immediately on mount or URL change and schedule another check 15 seconds after each completed check. They keep the last result visible during rechecks. Results stay in component state, not saved profiles. URL edits and leaving/deleting a card cancel its pending probe and recheck timer; outdated results are ignored.

Online means an OBS endpoint is reachable from this browser, not that its password is correct or Studio Mode is enabled. Offline also covers timeouts, non-OBS endpoints, and browser/network restrictions. Connect remains available regardless of the badge result; authentication and session setup happen after the operator chooses Connect or during the single startup restoration attempt described above.

## Current limitations to consider when changing behavior

- Newly configured transitions can be loaded with the appbar refresh button; there is no transition-list event subscription.
- Synchronization errors are displayed and release the syncing flag; the previous snapshot may remain visible. A connected status alone does not prove a fresh snapshot.
- The fallback timeout can unlock controls during unusually long transitions. Externally started transitions rely on the video-end event for unlocking; interrupted transitions require real OBS validation.
- Scene selections are tracked by names, not UUIDs. Renames trigger a refresh.
- Validation includes a simulated OBS protocol server, DOM tests, and a targeted read-only scene-order check against real OBS. Full OBS/browser acceptance remains outstanding; see milestone acceptance notes.

Consult the [OBS protocol](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md) and [client documentation](https://github.com/obs-websocket-community-projects/obs-websocket-js) when changing protocol interactions. Installed types and the current implementation remain the immediate references for supported calls.
