# Screenshot monitor research

Researched 2026-11-12 against primary sources. This is implementation research for the [M3 scope](milestones.md#m3--preview-and-program-video), not an implementation or live acceptance result. Read `AGENTS.md`, architecture, milestones, and development guidance. No GPL implementation was copied; recommendations below describe an independent React design.

## What OBS Blade does

The supplied [dashboard starting URL](https://raw.githubusercontent.com/Kounex/obs_blade/master/lib/stores/views/dashboard.dart) is mutable. Findings use OBS Blade commit `4b3fb4127c7774d2690bfb5f122fbddac24106a4`.

- **Pacing:** one screenshot in flight, driven by responses, with a one-second retry after failure. Successful LAN responses immediately trigger another request. A new stream clears the in-flight slot; a suspension gate stops fetching unseen frames. This bounds request concurrency, not frame rate or decoding work. [Dashboard, request loop](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/stores/views/dashboard.dart#L987-L1113)
- **Remote cap:** relay requests have a 250 ms minimum start-to-start interval (at most 4/s), subtracting elapsed request time rather than adding 250 ms after every response. Its comments report socket congestion and delayed control replies as motivation; that is upstream experience, not a measurement of studioctrl. [Remote pacing](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/utils/remote/remote_pacing.dart)
- **Encoding:** initially JPEG, falling back to PNG when neither JPEG alias is advertised; quality is `-1`. Width uses the device's physical short side, clamped to 320–1920 (1280 fallback), then capped by OBS base width. Height is omitted. [Defaults](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/stores/views/dashboard.dart#L396-L399), [request/width](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/stores/views/dashboard.dart#L1102-L1112), [width calculation](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/stores/views/dashboard.dart#L1356-L1366), [format negotiation](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/stores/views/dashboard.dart#L2524-L2544)
- **Target/response:** ordinarily screenshots the active Program scene; exposed Studio controls select Preview instead. It tags the request with its scene, base64-decodes the response, applies the frame, then advances polling. [Target](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/stores/views/dashboard.dart#L1093-L1112), [response](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/stores/views/dashboard.dart#L3089-L3099)

**Smoothness:** the image widget uses `Image.memory` with `gaplessPlayback: true`, retaining the old image during replacement. Its transition overlay waits for decoded images, shares Flutter's image cache, disposes retained image handles, and checks mount/transition identity after asynchronous decoding. This is not a video jitter buffer or decode-paced polling. [Image widget](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/views/dashboard/widgets/dashboard_content/scene_preview/scene_preview_image.dart); [Flutter's gapless behavior and stale-image caveat](https://api.flutter.dev/flutter/widgets/Image/gaplessPlayback.html).

**Ordering:** the transition tracker retains the displayed frame and at most one held incoming frame, replacing held bytes with newer arrivals. Defaults bound unresolved holds to 400 ms, transition context to three seconds, and outgoing-frame age to three seconds. Reset discards that context. These are animation safeguards, not comprehensive session/request generation checks; a same-scene frame bypasses transition animation. [Tracker](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/utils/preview_transition/preview_transition_tracker.dart).

## OBS contract and Program limitations

`GetSourceScreenshot` accepts inputs/scenes and returns base64 `imageData`. Formats come from `GetVersion`; dimensions are optional, 8–4096, and unspecified dimensions default to source resolution. Quality accepts `-1` (encoder default) through 100. The protocol describes aspect-preserving inner scaling. [Pinned protocol](https://github.com/obsproject/obs-websocket/blob/e28f84975984340e84fc4879cfc05741cc0afde1/docs/generated/protocol.md#getsourcescreenshot).

The handler renders the selected source, reads pixels back from graphics memory, encodes through Qt, and returns a `data:image/...;base64,...` URL. It rejects transition sources. Width-only derives height from source aspect; notably, the inspected implementation sets both supplied dimensions directly despite the protocol's inner-scaling description. Prefer width-only and contain the result in the monitor. Screenshotting temporarily increments source “showing,” so it is not necessarily free of source lifecycle effects. [Screenshot handler](https://github.com/obsproject/obs-websocket/blob/e28f84975984340e84fc4879cfc05741cc0afde1/src/requesthandler/RequestHandler_Sources.cpp#L28-L234).

**A screenshot of the Program scene name is not an authoritative Program output frame.** OBS Studio Mode can duplicate the scene privately for output, preserving separate scene-item state; its Program identity still refers to the original source. Meanwhile screenshot name lookup resolves the ordinary source. Therefore, with scene duplication enabled, editing transforms/visibility in Preview can make a screenshot labeled Program show uncommitted edits, even when both panels report the same scene. Private references also need not isolate all shared input properties. This conclusion follows from source inspection and requires live reproduction on the supported OBS version. [OBS scene duplication/output transition](https://github.com/obsproject/obs-studio/blob/fe1ed7955f300efd17fc59f65938388e43d8bb06/frontend/widgets/OBSBasic_Transitions.cpp#L295-L367), [screenshot source lookup](https://github.com/obsproject/obs-websocket/blob/e28f84975984340e84fc4879cfc05741cc0afde1/src/requesthandler/rpc/Request.cpp#L231-L266).

Likewise, named-scene screenshots exclude the mixed transition output, stinger video, and fade-to-black composition. OBS Blade synthesizes local transitions from outgoing/incoming frames; this improves appearance but cannot verify actual output. Scene identity alone cannot detect a same-scene transition, and the tracker explicitly treats same-scene arrivals as ordinary frames. [OBS output transition source](https://github.com/obsproject/obs-studio/blob/fe1ed7955f300efd17fc59f65938388e43d8bb06/frontend/widgets/OBSBasic_Transitions.cpp#L274-L367), [Blade tracker](https://github.com/Kounex/obs_blade/blob/4b3fb4127c7774d2690bfb5f122fbddac24106a4/lib/utils/preview_transition/preview_transition_tracker.dart). For stingers, `SceneTransitionEnded` represents the cut point; `SceneTransitionVideoEnded` indicates video completion. [Protocol events](https://github.com/obsproject/obs-websocket/blob/e28f84975984340e84fc4879cfc05741cc0afde1/docs/generated/protocol.md#scenetransitionvideoended).

## Recommendations for independent React implementation

These are proposed starting choices, not measured optimal settings:

1. Own one scheduler per OBS session, separate from control-state synchronization. Start with a shared budget of four screenshot requests/s total, alternating enabled Preview/Program panels, and one request in flight globally. Wait for response and decoding before scheduling the next; subtract elapsed time from the interval. Pause while hidden/disabled/disconnected. Back off failures; keep controls usable.
2. Negotiate an exact advertised JPEG spelling, otherwise supported PNG. Start at width 640 and JPEG quality 70; adjust from panel CSS width and capped device pixel ratio, bounded by source dimensions and protocol limits. Measure payload size, OBS load, decode time, and control latency before raising rate/resolution. Preserve aspect with width-only and `object-contain` in the existing fixed monitor frame.
3. Keep one displayed image and one candidate per panel. Decode the candidate off-DOM with `HTMLImageElement.decode()`, then swap the decoded element on an animation frame. Retain the previous image only for the same target while decoding; avoid crossfading ordinary frames. Drop failed candidates and release obsolete buffers/URLs. The HTML standard explicitly supports decode-before-insertion and animation-frame presentation. [HTML image decoding](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode)
4. Capture session generation, collection revision, panel role, source identity, target revision, and request sequence at dispatch. Recheck after response, after decode, and before display. Invalidate on Exit, reconnect, collection switch, target/role change, disable, and unmount. Clear misleading old-target pixels immediately; keep the scene-name fallback. Pair displayed metadata with the accepted frame, and visibly mark aged frames unavailable/stale.
5. Use finite request deadlines, but remember a client timeout does not cancel OBS rendering or remove bytes already queued on the socket. Discard late replies by generation/sequence; avoid repeated retries that accumulate unresolved work. Do not let an old completion release a newer request's slot. Handle React effect cleanup/Strict Mode without starting duplicate loops.
6. Describe Program as a scene screenshot approximation and show transition status from OBS events. Do not simulate a transition as proof of output or assume matching scene names justify sharing an authoritative Program frame. Require an actual Program-output transport if broadcast confidence monitoring is the requirement. Preserve explicit Preview selection and transition actions.

Outstanding validation: no app implementation, browser QA, throughput measurements, or live OBS checks performed. Validate rapid scene changes during response/decode, same-name scenes across collections/sessions, reconnect/unmount, hidden tabs, corrupt frames, stalls, non-16:9 sources, duplication/edit-properties modes, same-scene takes, Cut/Fade/stingers, fade-to-black, and interrupted/manual transitions. Existing implementation contracts and milestone status remain unchanged.

## Implementation follow-up

The current independently written implementation is documented in [architecture](architecture.md#screenshot-previews), with actual acceptance status in [milestones](milestones.md#m3--preview-and-program-video). It uses two monitor loops capped at 10 FPS each and quality 65, rather than the conservative initial four-request/s recommendation above. Live screenshot width now follows each monitor's viewport and device pixel ratio as described in architecture; the original local capture check below used fixed width 640. A local read-only capture check reached the chosen cap without errors; browser smoothness and broader load validation remain outstanding. The research observations and recommendations above are separate from that implementation evidence.
